# 03: Регулярне оновлення та історія метрик

Part of [#1](https://github.com/virus231/channel-radar/issues/1).

**What to build:** Канали оновлюються за розкладом без дублікатів постів, counters
накопичуються як часові спостереження, а помилки джерела видимі й не стирають дані.

**Blocked by:** [#3](https://github.com/virus231/channel-radar/issues/3).

**Status:** ready-for-agent

## Acceptance criteria

- [ ] Перший і регулярний збір використовують одну операцію; пагінація дістає всі нові доступні пости до checkpoint.
- [ ] Повтор тієї самої спроби не дублює пости або спостереження; новий timestamp додає нову точку історії.
- [ ] Counters відомих постів із отриманих сторінок оновлюються навіть без нових постів; старі спостереження зберігаються.
- [ ] Частковий збій не просуває checkpoint повз незавершений діапазон; наступний збір відновлює його ідемпотентно.
- [ ] Перекриття додавання/cron не запускає два збори одного каналу; restart не залишає канал назавжди заблокованим у collecting.
- [ ] Внутрішній POST тригер потребує Authorization token і швидко повертає 202; health check не звертається до БД.
- [ ] cron-job.org викликає health кожні 10 хвилин і збір кожні 30; виконання перевірено за даними, а не лише HTTP-відповіддю.
- [ ] Стани джерела показують last attempt/success, безпечну помилку й stale після 90 хвилин; відсутність нових постів не є помилкою.
- [ ] Offline collection tests покривають повтори, зміну counters, пагінацію й часткові збої; live PostgreSQL/restart check підтверджує production поведінку.

## Verification

Два фіксовані observed_at з fixtures у pytest; mocked HTTP для багатосторінкового
збору; відхилення неправильного scheduler token. Окремо — два збори реального
каналу, повтор, restart і історія зовнішніх jobs на deployed сервісі.
