# Channel Radar — специфікація MVP

**Статус:** затверджений план; почато першу задачу, базовий запуск. MVP ще не завершений.
**Джерело вимог:** [TEST-TASK.md](TEST-TASK.md).
**План і задачі:** [development-plan.md](development-plan.md).

## Проблема

Користувачу потрібне одне робоче посилання, за яким він додає публічний
Telegram-канал, бачить його пости й динаміку доступних метрик та отримує корисне
резюме. CLI-скрипт або репозиторій без живого сервісу не завершують завдання.

## Рішення та межі

Один застосунок: FastAPI API і зібраний React на Render Free; PostgreSQL у Neon
Free. Анонімний збір з `https://t.me/s/<username>` запускається при додаванні каналу
та зовнішнім розкладом. Gemini створює кешований дайджест збережених постів.

Стек: Python 3.12, uv, FastAPI, SQLAlchemy, Alembic, HTTPX, BeautifulSoup;
React, TypeScript, Vite, React Router, TanStack Query, Recharts, npm.
Залежності фіксуються `uv.lock` і `package-lock.json` у першій задачі реалізації.
Продакшн — один Uvicorn worker і один Render instance, без окремого воркера.
UI та документація MVP — українською; тексти постів зберігають оригінальну мову.

Масштаб перевірки — приблизно десять каналів. Автентифікація, ролі, Telegram Bot API,
Celery, Redis, платні плани, порівняння каналів, алерти, експорт `pulse` і власна
дизайн-система не входять у MVP. Внутрішній scheduler token захищає тільки тригер
збору й не створює користувацької автентифікації.

## User stories

1. Як користувач, я відкриваю публічний URL і одразу бачу стан каналів.
2. Я вводжу username або `@username` у форму без Telegram-ключів.
3. Після відправлення я бачу канал у списку та стан першого збору.
4. Я розумію, що канал недоступний, приватний або не має web-прев’ю.
5. Повторне додавання того самого username показує існуючий канал.
6. Я бачу підписників, кількість збережених постів і час останнього успішного збору.
7. Я можу відрізнити здорове джерело без нових постів від помилки збору.
8. Я відкриваю канал, вибираю період і бачу відповідні пости та графіки.
9. Я відкриваю пост, читаю його текст і переходжу до оригіналу в Telegram.
10. Я бачу перегляди й реакції, а відсутні метрики відрізняю від нуля.
11. Я отримую дайджест періоду з темами та посиланнями на використані пости.
12. Повторний запит незміненого дайджесту працює з кешу.
13. При недоступному LLM я продовжую користуватися дашбордом і можу повторити AI-запит.
14. Як рев’юер, я запускаю тести без мережі й ключів та розумію рішення з документації.

## Збір і стани

Username нормалізується: trim, видалення одного початкового `@`, нижній регістр.
Приймаються тільки Telegram usernames із літерами ASCII, цифрами й `_`; довільні
URL та адреси серверів не приймаються. Запити формуються лише для фіксованого
Telegram origin. Відповідь Telegram перевіряється як web-прев’ю каналу, а не як
довільна успішна HTML-сторінка.

`POST /api/channels` зберігає канал і запускає перший фоновий збір, не чекаючи
Telegram або Gemini. React опитує статус кожні 2 секунди, доки збір активний.
Для теплого сервісу орієнтир першого результату — до 10 секунд при доступному
Telegram; це перевіряється на живому сервісі, а не обіцяється без вимірювання.
Перший збір читає одну останню сторінку прев’ю; повного історичного backfill немає.

Під час регулярного збору читати останню сторінку й рухатися `?before=<message_id>`
назад, поки не досягнуто останнього збереженого ID або кінця прев’ю. Зберігати нові
пости й оновлювати текст відомих постів, які трапилися в отриманих сторінках.
Не покладатися на послідовність номерів: видалені пости можуть залишати пропуски.
Оновлення динаміки метрик охоплює пости, фактично присутні в отриманих сторінках;
старі пости поза ними не опитуються окремо. Не видаляти з БД пост лише тому, що він
більше не присутній у прев’ю.

Кожна успішна спроба записує спостереження навіть без нових постів. Повторне
збереження того самого набору з тим самим `observed_at` не створює дублікатів.
Новий успішний збір з іншим часом — нове спостереження. Checkpoint нових ID
просувається тільки після завершення інкрементального проходу; при частковому
збої наступна спроба перечитує незавершений діапазон і безпечно повторює записи.

Одночасні збори одного каналу серіалізуються в одному worker; перекриття викликів
не запускає другий збір цього каналу. Це локальна координація, не черга задач.
Після перезапуску всі канали можуть бути повторно зібрані наступним scheduler
викликом, незалежно від збереженого стану `collecting`; він не є постійним lock.

| Стан | Значення для UI |
|---|---|
| pending | Канал збережений, перший збір очікується |
| collecting | Зараз виконується збір |
| ready | Останній збір успішний, включно з порожнім каналом |
| unavailable | Канал не має доступного публічного прев’ю |
| error | Timeout, HTTP-помилка або непридатна структура відповіді |

Показувати окремо останню спробу, останній успіх і коротку безпечну причину помилки.
Збережені дані не зникають через збій. Понад 90 хвилин без успішного збору
позначаються як застарілі дані. Відсутність нових постів не змінює здоров’я джерела.

## Дані та аналітика

| Сутність | Дані та обмеження |
|---|---|
| channels | ID, унікальний normalized username, назва, стан, last attempted/successful collection, безпечна причина останньої помилки |
| posts | Композитний ключ `(channel_id, message_id)`, час публікації, plain text, original URL; тільки FK до відомого каналу |
| channel_observations | Ключ `(channel_id, observed_at)`, кількість підписників або `null` |
| post_observations | Ключ `(channel_id, message_id, observed_at)`, перегляди або `null`, карта доступних реакцій або `null` |
| digests | Канал, межі періоду, input fingerprint, модель, стан, згенерований текст/теми з message IDs, generated_at, безпечна причина помилки; унікальний ключ кешу за каналом, періодом, fingerprint і моделлю |

Всі часові значення зберігаються й повертаються в UTC. Історія починається з першого
спостереження; попередні точки на графіку не вигадуються. Відсутні counters — `null`,
не нулі. Сирий HTML не віддається в UI; текст постів показується як текст без
`dangerouslySetInnerHTML`. Приховані реакції або недоступні media не домислюються.

Огляд показує останнє спостереження підписників, число збережених постів, стан і час
останнього успіху. Сторінка каналу має графік підписників за часом спостереження,
кількість збережених постів за днями публікації, список постів і середні перегляди
для вибраного періоду. Деталі поста показують останні counters та історію їх змін.

Середні перегляди = сума останніх відомих переглядів постів у періоді / кількість
постів із відомими переглядами. `null` виключається зі знаменника; якщо відомих
значень немає, результат `null`. Значення 100, 300, null дають 200; 0 і 100 дають 50.
Приріст підписників — різниця останнього й першого відомого спостереження у періоді;
для менш ніж двох відомих точок приріст невідомий.

У UI період за замовчуванням — останні 7 календарних днів UTC включно із сьогодні.
Вибрані дати включають обидва дні; API отримує UTC-північ початку й північ дня
після останнього, тобто напіввідкритий інтервал `[from, to)`. Фільтр постів і
дайджесту використовує published_at, графік підписників — observed_at.
Покриття збором вказується поруч, щоб вибір періоду не обіцяв повноти Telegram-архіву.

## API contract

JSON API під `/api`; дати — ISO 8601 UTC. Базові помилки мають короткі машинний code
і user-facing message. Автоматичну валідацію параметрів виконує FastAPI/Pydantic.
Ідентифікатори невідомих каналів і постів повертають 404.

| Метод і шлях | Вхід | Результат |
|---|---|---|
| GET /api/channels | — | Список каналів із ключовими цифрами й здоров’ям джерела |
| POST /api/channels | `{ "username": "@durov" }` | 202 + збережений канал і стан; 200 + існуючий канал при повторному username |
| GET /api/channels/{id} | — | Канал, статус, час спроби/успіху, покриття збором |
| GET /api/channels/{id}/posts | `from`, `to`, `limit=20`, optional `before_message_id` | Пости за спаданням message_id, останні метрики й cursor наступної сторінки |
| GET /api/channels/{id}/metrics | `from`, `to` | Підписники за часом, posts/day і середні перегляди |
| GET /api/channels/{id}/posts/{message_id} | — | Текст, оригінал, останні метрики та історія спостережень |
| GET /api/channels/{id}/digest | `from`, `to` | Поточний стан кешу, ready результат або null за відсутності спроби |
| POST /api/channels/{id}/digest | UTC-період у JSON полях `from` і `to` | 200 для готового актуального кешу/порожнього періоду, 202 для генерації або вже активної спроби |
| POST /api/internal/collect | `Authorization: Bearer <COLLECTOR_TOKEN>` | 202, запущено фоновий прохід каналів; 401 для невірного/відсутнього token |
| GET /healthz | — | 200 + `{ "status": "ok" }`, без БД, Telegram і LLM |

Канал повертає щонайменше `id`, `username`, `title`, `status`, `subscribers`,
`post_count`, `last_attempt_at`, `last_success_at`, `last_error`, `stale`.
Пост — `channel_id`, `message_id`, `published_at`, `text`, `original_url`,
`views`, `reactions`, `observed_at`. Відсутні значення допускають `null`.
Списковий limit валідний у межах 1–100; період має задовольняти `from < to`.

React routes: `/`, `/channels/:id`, `/channels/:id/posts/:messageId`.
FastAPI обслуговує API перед SPA fallback; невідомий API route лишається 404,
а пряме відкриття/перезавантаження React route повертає index.html.

## Дайджест

Використовувати збережені текстові пости за період у порядку публікації, не нові
Telegram-запити. Для однієї генерації брати до 100 останніх текстових постів,
до 2 000 символів кожного й до 40 000 символів разом. Якщо зріз обрізаний,
UI показує кількість використаних/доступних постів і попередження про неповне покриття.
Порожній період або відсутність текстів не викликають LLM.

Fingerprint будується з фактично переданих message IDs і текстів, а не з counters:
нова реакція не повинна без потреби перевикликати текстовий дайджест. Зміна тексту
або набору вхідних постів робить попередній кеш застарілим.
LLM повертає українське резюме й теми з message IDs. Backend валідовує форму та
належність IDs до входу, після чого сам формує Telegram-посилання. Тексти постів
передаються як дані з явним розділенням від інструкцій; LLM не отримує tools/secrets.

Поки генерація активна, UI показує стан і опитує його кожні 2 секунди. Timeout
LLM — 20 секунд. 429/5xx, timeout і невалідний результат переводять тільки цю спробу
в error; автоматичного циклу повторів немає. Користувач може явно повторити її.
Попередній успішний дайджест лишається доступним як застарілий. Збір не викликає LLM.

## Деплой та конфігурація

Один multi-stage Docker build: npm збирає React; Python image містить backend і
готовий frontend. Render Free запускає застосунок на своєму PORT; startup застосовує
Alembic migrations до Neon перед запуском єдиного worker. Для одного instance немає
гонки кількох міграторів. `/healthz` — HTTP health check.

Production settings: `DATABASE_URL` із SSL, `GEMINI_API_KEY`,
`GEMINI_MODEL=gemini-3.5-flash-lite`, `COLLECTOR_TOKEN`; Render також задає `PORT`.
DB/LLM/token зберігаються в environment settings. cron-job.org знає лише URL і
token збору в Authorization header. Credentials не передаються в query string.

Два зовнішні jobs: GET `/healthz` кожні 10 хвилин і POST `/api/internal/collect`
кожні 30 хвилин. Для другого 202 означає прийняття роботи, а успіх збору перевіряється
за станами каналів. Помилки зовнішніх jobs відстежуються в їхній історії виконань;
застарілість/помилки конкретних каналів видно в дашборді й безпечних логах backend.

Render засинає після 15 хвилин без HTTP-трафіку; пробудження може тривати близько
хвилини. 10-хвилинний health job знижує ризик сну, але не гарантує uptime. Якщо
cron-job.org перериває холодний запит на 30-й секунді, Render може продовжити
пробудження; наступний job повторює спробу. Перевірити це до демонстрації.
Render має спільні 750 free instance hours на workspace/місяць та інші квоти;
не використовувати локальну SQLite як production storage.

Neon Free на дату плану: 1 GB storage/project, 100 CU-hours/project/month і scale
to zero. Не тримати БД активною health-запитами; не ставити мінімальний постійний
compute. Перевірити поточний quota meter перед здачею. GitHub repo публічний за
рішенням користувача; Render може клонувати його без приватного доступу.

Умови перевірені 2026-10-08: [Render](https://render.com/docs/free),
[Neon](https://neon.com/blog/neon-free-plan-1-gb-per-project),
[cron-job.org](https://cron-job.org/en/faq/),
[Gemini free tier](https://ai.google.dev/gemini-api/docs/pricing).
Конкретні квоти й доступність моделі для акаунта перевірити перед provisioning.

## Узгоджені перевірки

Тестові інтерфейси: HTML → нормалізовані дані; збір → збережені пости/спостереження;
збережені спостереження → analytics; HTTP digest operation → кеш/помилки.
Тести перевіряють поведінку, а не приватні методи. Ці межі погоджені планом.

- Pytest: заборонити мережу через pytest-socket; transport API in-process;
  тимчасова SQLite БД; без `.env`, Telegram або LLM credentials.
- Parser fixtures: plain text/multiline, counters `1.2K → 1200`, `2.5M → 2500000`,
  missing counters, reactions, media-only post, ID gaps, порожній канал і
  сторінка без публічного прев’ю.
- Collection: повтор однієї спроби не дублює пости/спостереження; новий час збору
  додає історію; пагінація дістає нові пости поза першою сторінкою; частковий збій
  не втрачає діапазон; джерело без нових постів залишається здоровим.
- Analytics: відомі приклади середнього, невідомі значення, нулі, межі UTC-періоду,
  недостатня історія для приросту.
- API/UI: нормалізація й повторний username, 202/polling, unavailable/error/empty,
  pagination, token rejection, health без БД; Vitest + React Testing Library із
  mocked API для асинхронних станів; TypeScript check і production build.
- AI: mocked success, cache hit, зміна тексту, порожній/обрізаний зріз, 429,
  timeout, невалідні IDs; після помилки загальний API працює.
- Окремо від offline тестів: запуск проти PostgreSQL, міграції з порожньої БД,
  живий Telegram/Gemini і браузерний smoke на deployed URL. Ці перевірки не
  підміняються SQLite, фікстурами чи замоканим AI.

## Готовність повного MVP

Рев’юер відкриває URL, додає `@durov`, бачить стан і реальні дані, відкриває канал,
період і пост, генерує дайджест. Перезапуск не втрачає дані, два збори показують
динаміку, а повторний збір не дублює пости. README містить URL, перевірені local
commands, пояснення даних/AI/хостингу, обмеження та 3–5 речень для здачі. Всі
обов’язкові перевірки пройшли, репозиторій доступний рев’юеру, секретів у Git немає.

Цей критерій стосується наступної реалізації; поточна підготовка не є готовим MVP.
